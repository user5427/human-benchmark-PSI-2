\section{CI/CD}
This section will discuss continous integration and continous delivery of the application. 
The CI (continous integration) is the first process that is done which is then followed by CD (continous delivery).
For the CI/CD process we used GitLab CI/CD pipeline, .Net, Node, Docker, and OpenNebula virtual machine. The pipeline is triggered when a developer pushes his commit to a branch that has CI/CD action script.

\subsection{CI}
The CI (continious integration) is a process where where the application is built and tested after a developer pushes his commit to 
a branch that has CI action script. 

\subsubsection{CI order}
The CI is done in this order:
\begin{itemize}
    \item Stage 1: build the application (The order in which the application is built does not matter, the frontend or backend build process does not depend on each other).
    If building of frontend or backend fails, the CI is cancelled. \\ During this stage, the developer can manually trigger the versioning process \ref{sec:versioning}.
    \item Stage 2: test the application (Tests are done to frontend and backend in random order just like in the build stage).
    IF testing of frontend or backend fails, the CI is cancelled.
\end{itemize}

In case CI fails, a red 'X' appears near the commit message in GitLab.
The developer could be informed by an email or other types of communication that the CI proccess for his commit has failed but this is beyond our 
focus.

\subsubsection{CI commands}
The CI process usually is quite straight forward and in our case requires the use
of the basic \textbf{dotnet} and \textbf{npm} commands. These exact commands are used to build the backend:
\begin{enumerate}
    \item \texttt{dotnet restore}
    \item \texttt{dotnet build --configuration Release}
    \item \texttt{dotnet publish -c Release -o ./publish}
\end{enumerate} 
To build the frontend:
\begin{enumerate}
    \item \texttt{npm install}
    \item \texttt{npm run build}
\end{enumerate}

\subsection{CD}
The CD (continous delivery) is a process where the application is 
dockerized using Docker and then deployed to a hosting service (in our case our faculty virtual machine).

\subsubsection{CD order}
The CD is done in this order:
\begin{itemize}
    \item Stage 3: dockerize the application (The order in which the application is dockerized does not matter, the frontend or backend build dockerization does not depend on each other).
    If dockerization of frontend or backend fails, the CD is cancelled.
    \item Stage 4: update database (The database is updated with the latest changes). This stage is optional and can be triggered manually.
    \item Stage 5: deploy the application (The application is deployd to VM)
    IF deployment fails, the CD is cancelled.
\end{itemize}

In case CD fails, a red 'X' appears near the commit message in GitLab.
Just like in CI section, the developer could be informed by other means but this is beyond the scope of our document.

\subsubsection{CD commands}
The CD process just like CI is straight forward and in our case requires the use
of the basic \textbf{docker} commands. These exact commands are used to dockerize the backend and frontend:
\begin{enumerate}
    \item \texttt{docker build -t frontend-app .}
    \item \texttt{docker build -t backend-app .}
\end{enumerate}

In both cases the docker service finds the images necessary to run the frontend and backend automatically.
Then the developer can choose to update the database with the latest changes. The command \texttt{dotnet ef database update} is used to update the DB.
And lastly the command \texttt{docker-compose up -d} is used to deploy the application.

\subsection{Versioning}

Updates to this database must be done manually (can be triggered in CI/CD pipeline) by the developer to avoid unexpected data loss.

We use GitLab runner on our VM machine to execute the CI/CD pipeline. ]This ensures that our pipeline remains simple as hosting is also done by the same VM.

\subsubsection{Storage requirements}
As previously in sections CI and CD we discussed, the building and images of the application take 
up around 3 gigabytes in total (300 MB files and 2.5 gigabytes from all the images, including .Net and Node).

Furthermore, the Debian 12 minimal console only installation takes up around 2 gigabytes. In total, the system would require at least 
5 to 6 gigabytes for functioning. However, as the application will improve, it is likely that it will require more storage.
Ideally it would be better to assign somewhere around 10 gigabytes to the virtual machine. In our case, we assigned 20 gigabytes.

User files will be stored on database and not on the VM. As a result, the storage requirements for the VM are quite low.

\subsubsection{Threats and mitigations}
Both pipeline and hosting runs on the same machine. A catastrophic failure in CI/CD could bring down the VM, including the website. This would cause downtimes for the users.
It would be better to host the website on cloud services like Azure, however, because we had to use GitLab, our team was uncertain how the 
GitLab CI/CD process would communicate with the Azure as our faculty VPN may be troubling. To mitigate this threat, our team would need to switch to Github and setup Azure hosting.
Furthermore, the machine has SSH setup on it, which means if the password was to be found for it, an attacker could gain access to the VM and potentially compromise the entire system. To mitigate this threat, it is crucial to implement strong password policies, regularly update passwords, and consider using SSH key-based authentication instead of password-based authentication. 
Additionally, monitoring and logging SSH access attempts can help in identifying and responding to potential security breaches promptly.
