\sectionnonum{Introduction}
This document presents the request to add real-time chat capabilities to the reaction time training web application. The goal is to improve user interaction  by allowing communication globally and within specific game rooms.

\section{Description}
Create a chat system enabling users to send and receive text-based messages. This system will operate in two scopes:
\begin{itemize}
\item Global scope. Accessible to all logged-in users outside of active game rooms.
\item Room scope. Accessible only to users currently participating within the same active game room.
\end{itemize}
\section{Initial Requirements}

\begin{itemize}

    % UI Structure
    \item The UI shall include a togglable chat panel displayed on the right side of the application when the user is logged in.
    \item The chat panel shall display a title at the top to indicate its scope:
    \begin{itemize}
        \item \texttt{Global} - all users are able to send, view messages.
        \item \texttt{Room <room-name>} - restricted to users who are currently inside the same active game room.
        \item \texttt{Group <group-name>} - restricted to specific set of users who have been granted access to that group.
        \item \texttt{Private <receiver-username>} - direct one-to-one communication between two users.
    \end{itemize}
    \item The panel shall include the following UI elements:
    \begin{itemize}
        \item A scrollable area for message display.
        \item A text input field for message creation, limited to 255 characters.
        \item A \texttt{Send} button for message submission.
    \end{itemize}

    % Message Display
    \item System shall display each display message with the following details:
    \begin{itemize}
        \item Sender's username.
        \item Message timestamp (formatted as \texttt{HH:MM} or similar).
        \item The actual text content.
    \end{itemize}
    \item Messages must be ordered chronologically, with the most recent messages appearing at the bottom.

    % Message Handling
    \item Typing a message and either clicking the \texttt{Send} button or pressing the \texttt{Enter} key shall send the message to the server.
    \item After sending a message:
    \begin{itemize}
        \item The input field must be cleared.
        \item The message must immediately appear in the sender's chat panel.
        \item Other users in the same chat scope (global or room) must receive the message in real time.
    \end{itemize}
    \item When the user opens the chat panel for the first time, the system shall fetch and display a list of past messages relevant to that chat scope.
    \item If an error occurs during sending:
    \begin{itemize}
        \item A popup notification must appear with the message \texttt{"Failed to send message"}.
        \item The notification must disappear after 3 seconds or when manually closed by the user.
    \end{itemize}
    \item For each received message, the system shall determine the correct destination:
    \begin{itemize}
        \item If the message is a direct message to another user, the scope is \texttt{Private <receiver-username>}.
        \item If the message is sent to a specific group, the scope is \texttt{Group <group-name>}.
        \item If the message is sent to a game room, the scope is \texttt{Room <room-name>}.
        \item If the message is broadcasted publicly outside of any room or group, the scope is \texttt{Global}.
    \end{itemize}
\end{itemize}

\section{Impact Analysis}

\subsection{System}
The introduction of a messaging feature to the existing system represents a significant change in terms of functionality. However, since it is being developed as an entirely new module, the impact on the core functionality of the current system is expected to be minimal or negligible. This modular approach helps in isolating the new feature from existing components, thereby reducing the risk of unintended side effects.

\subsection{Maintainability}
While the core system may remain unaffected, the overall maintainability of the project could be impacted. The addition of messaging introduces new components, interfaces, and possibly data structures, increasing the codebase’s complexity and size. This can lead to a steeper learning curve for future developers and more effort required for debugging and testing. Proper documentation and adherence to architectural standards will be essential to mitigate these challenges.

\subsection{Cost and Stakeholders}
The implementation cost is non-trivial, as it involves backend development (e.g., message storage, delivery systems), frontend integration (user interface and notifications), and possibly infrastructure changes (e.g., database or server scaling). This will directly impact stakeholders, particularly in terms of budget allocation, resource planning, and delivery timelines.

\subsection{User Experience}
In the early stages of the feature rollout, users may experience confusion or require time to adapt to the new user interface elements introduced by the messaging system. This can lead to temporary dips in user satisfaction or increased support requests. Providing clear onboarding, tooltips, and possibly a brief tutorial or announcement can ease the transition.

\subsection{Performance Considerations}
Depending on the implementation, real-time messaging or high volumes of communication can introduce performance challenges, especially under load. It will be important to test for scalability and responsiveness during peak usage.

\subsection{Security and Compliance}
Messaging introduces potential security concerns, such as message encryption, data privacy, and user abuse prevention. Ensuring that the messaging system adheres to relevant compliance and data protection standards (e.g., GDPR) is critical.

\subsection{Opportunities}
On the positive side, this change opens the door to increased user engagement, improved collaboration, and potential monetization strategies (e.g., premium messaging features). It also positions the product competitively in markets where integrated communication is a strong differentiator.

\section{Implementation options}

\subsection{Develop from scratch}
This involves building the entire chat system end-to-end, including extending database, services and using web sockets for real time communication, as well as developing custom  React components for the chat interface and later maintaining it.
\subsubsection{Pros}
\begin{description}
    \item[Flexibility] Features are not limited to 3rd party capabilities. We can fully develop features, UI/UX, manage data, and integrate new features within existing codebase.
    \item[No 3rd party costs] Avoids recurring subscription fees, which may rise in the future. Costs shift towards infrastructure and maintenance, which can be be lower than 3rd party service costs.
    \item[Data ownership] User data is not stored in extenal database, so we do not rely on 3rd party policies or security measurements for stored user data.
\end{description}
\subsubsection{Cons}
\begin{description}
    \item[High initial investment]  Requires huge time and resource allocation for chat feature development.
    \item[Increased infrastructure costs] Real time chat functionality will increase  Infrastructure(power, data storage, bandwith) fees.
    \item[Risk of bugs] Specialized third-party service is often thoroughly tested and reliable, whereas building a solution from scratch increases the risk of introducing bugs.
\end{description}

\subsection{Use External communication application such as Discord}
 Instead of building chat features directly into the web app, users are encouraged to communicate via  external platform like a dedicated Discord server. 
\subsubsection{Pros}
\begin{description}
    \item[Minimal Development Effort] Requires no coding effort within the core web application itself, aside from potentially adding links or notes related to Discord.
    \item[Many existing features] Discord has rich text, voice channels, emote or file support, roles, bots, mobile apps, and many more.
    \item[No Infrastructure costs] All costs and complexities related to hosting, scaling, and maintaining the chat service are handled by the external platform.
    \item[User Familiarity] Many users may already be familiar with Discord.
\end{description}
\subsubsection{Cons}
\begin{description}
    \item[Poor Integration] Requires users to switch apps to chat, Can be disruptive to the user flow.
    \item[Manual setup for users] Room specific chat logic has to be handled by users.
    \item[Loss of Control] No control over the chat UI or platform availability.
\end{description}


\subsection{Use Third-Party Chat service - Stream}
Use a specialized commercial service that provides chat functionality  via an API and client-side SDKs, such as Stream. Application's frontend integrates the SDK to display chat UI elements, and backend interacts with the service's API to manage users and channels. The third party handles infrastructure.
\subsubsection{Pros}
\begin{description}
    \item[Faster development] Significantly reduces development time compared to building from scratch, as the core functionality is already built.
    \item[Managed infrastructure] Avoid managing WebSockets, scaling connections, ensuring reliability, and handling infrastructure maintenance.
    \item[Additional features included] Often comes with built-in features like presence indicators, typing notifications, message history, read receipts, and moderation tools.
    \item[Decent integration] Allows chat UI to be embedded directly within your web application.
\end{description}
\subsubsection{Cons}
\begin{description}
    \item[Provider costs] Monthly subscription fees based on usage metrics (Monthly Active Users, concurrent connections...) which can become significant if app is popular.
    \item[Difficulty to migrate] Integrating with a specific service makes it potentially difficult and costly to switch providers later.
    \item[Limited customization] Flexibility is bound by the features and customization options offered by the specific vendor; future requirements may be hard to implement.
    \item[External dependency] Chat functionality tied to the third-party service.
\end{description}

\subsubsection{Summary}
Developing from scratch offers the highest flexibility, but requires a high initial investment(assuming team of 3 seniors, all costs included 20.000-30.000€/month) and some ongoing maintenance costs. Using Discord is the cheapest and fastest option but sacrifices integration and control.  Third-party service Stream offers faster development with moderate recurring costs (starting around 400€ per month for up to 10,000 Monthly Active Users, 500 concurrent connections), which, however, could increase significantly as the app becomes more popular, and flexibility is limited by the external service capabilities.

\subsection{Step 1: Identify Duplicates and Similar Terms}
Let’s identify and examine candidate duplicates or terms that may not belong in the domain model:

\begin{itemize}
    \item \textbf{Chat Panel vs. Chat Scope vs. Destination Scope}
    \begin{itemize}
        \item Chat Panel is a UI element.
        \item Chat Scope and Destination Scope are very similar. Let's standardize on Chat Scope and drop "Destination Scope".
    \end{itemize}

    \item \textbf{Input Field vs. Text Input}
    \begin{itemize}
        \item These are describing the same UI element. Let’s keep Text Input.
    \end{itemize}

    \item \textbf{Message vs. Message Content vs. Message Display vs. Message List vs. Past Message}
    \begin{itemize}
        \item These are mostly part-of relationships with "Message".
        \item Let’s keep Message, and treat the rest as attributes or subcomponents of it.
    \end{itemize}

    \item \textbf{Notification vs. Popup Notification}
    \begin{itemize}
        \item “Popup” describes the form, not the concept. Let’s keep Notification.
    \end{itemize}

    \item \textbf{Sender Username vs. Sender vs. User}
    \begin{itemize}
        \item Redundant. We’ll keep only User.
        \item Sender is a role of the User in this context, so we can treat it as an attribute.
        \item Sender Username is a specific attribute of the User.
    \end{itemize}

    \item \textbf{User vs. Customer Account}
    \begin{itemize}
        \item These terms are essentially describing the same concept. Let’s standardize on User and drop Customer Account.
    \end{itemize}
\end{itemize}

\subsection{Step 2: Remove Out-of-Scope or Non-Domain Concepts}

These items are either:

\begin{itemize}
    \item Purely UI,
    \item Too low-level (like primitives), or
    \item Better handled in use cases or elsewhere.
    \item Room ID → implementation detail (likely an attribute).
    \item Message Order → implementation detail (likely an attribute).
    \item TextInput → UI element.
    \item Timestamp → implementation detail (likely an attribute).
\end{itemize}

Let’s remove the following:

\begin{itemize}
    \item \textbf{Character Limit} → implementation detail.
    \item \textbf{Title} → search parameters, not domain entities.
    \item \textbf{Input Sanitization} → non-functional concern (security).
    \item \textbf{UI Element} → overly generic placeholder.
\end{itemize}

\subsection{Step 3: Keep and Rename Where Needed}

Some items are useful but need better naming:

\begin{itemize}
    \item \textbf{System and Server} → Usually architectural layers, not domain entities. Remove.
    \item \textbf{REST Endpoint} → Implementation detail. Remove.
\end{itemize}

\section{Use cases}
Using the updated domain model and the UI mockups, we will try our best to create the use cases for the chat system.
It is likely that we will need to update our domain model once again after creating the use cases.

\subsection{Rough Draft of Use Cases}
Below is a rough draft of the use cases (these are not final, in fact, they do not even include the 'rainy-day' scenarios):
\begin{itemize}
    \item \textbf{Core Chat Functionality}
    \begin{itemize}
        \item \textbf{Send Message}
        \begin{itemize}
            \item User composes and sends a message to a chat (global, room, group, or private) using \textbf{chat section}.
            \item Includes text, emojis using \textbf{emoji list}, and file attachments using \textbf{file upload list}.
        \end{itemize}
        \item \textbf{Switch between Chats}
        \begin{itemize}
            \item User switches between different chat sections using \textbf{chat access point}.
            \item System limits number of concurrent chats.
        \end{itemize}
    \end{itemize}

    \item \textbf{Message Management}
    \begin{itemize}
        \item \textbf{Edit Message}
        \begin{itemize}
            \item User modifies a previously sent message using \textbf{chat section}.
            \item System preserves edit history.
        \end{itemize}
        \item \textbf{Delete Message}
        \begin{itemize}
            \item User removes a sent message (with confirmation) using \textbf{chat section}.
        \end{itemize}
        \item \textbf{Pin Message}
        \begin{itemize}
            \item User marks important messages in group/private chats using \textbf{chat section}.
            \item Pinned messages get special visibility.
        \end{itemize}
        \item \textbf{View Pinned Messages}
        \begin{itemize}
            \item User accesses pinned messages in a \textbf{pinned messages list}.
        \end{itemize}
        \item \textbf{Unpin Message}
        \begin{itemize}
            \item User removes the pinned status from a message using \textbf{pinned messages list}.
        \end{itemize}
        \item \textbf{Search Messages}
        \begin{itemize}
            \item User searches message history across different chats using \textbf{search messages section}.
        \end{itemize}
        \item \textbf{View Message History}
        \begin{itemize}
            \item User views past messages in a chat using the same \textbf{search messages section} but without inputting any search parameters.
            \item Messages displayed with sender, timestamp, and content.
        \end{itemize}
    \end{itemize}

    \item \textbf{Chat Management}
    \begin{itemize}
        \item \textbf{Switch Chat Scopes}
        \begin{itemize}
            \item User switches between global and room chat scopes using \textbf{chat access point} or when they are in the \textbf{game room}.
        \end{itemize}
        \item \textbf{Create Group Chat}
        \begin{itemize}
            \item User initiates a new group conversation using \textbf{chat creating section}.
            \item Specifies group name and adds participants.
            \item System limits number of concurrent chats.
        \end{itemize}
        \item \textbf{Join Group Chat}
        \begin{itemize}
            \item User requests to join an existing group using \textbf{chat creating section}.
            \item Group owner approves/rejects request.
        \end{itemize}
        \item \textbf{Manage Group Members}
        \begin{itemize}
            \item Group owner adds/removes participants using \textbf{group chat editing section}.
        \end{itemize}
        \item \textbf{Start Private Chat}
        \begin{itemize}
            \item User initiates 1:1 conversation with another user using \textbf{chat creating section}.
        \end{itemize}
        \item \textbf{Delete Chat}
        \begin{itemize}
            \item User removes a private or group chat (with confirmation) using either \textbf{private chat editing section} or \textbf{group chat editing section}.
        \end{itemize}
        \item \textbf{Change Chat Type}
        \begin{itemize}
            \item User switches between global, room, group, and private chat types using \textbf{chat access point}.
            \item System limits number of concurrent chats.
        \end{itemize}
    \end{itemize}

    \item \textbf{Notification System}
    \begin{itemize}
        \item \textbf{Receive Notification}
        \begin{itemize}
            \item System alerts user about new messages/events in the \textbf{notification list}.
            \item System alers user about invitations to join group chats in the \textbf{notification list}.
            \item System alers user about removal from group chats in the \textbf{notification list}.
            \item System alers user about deletion of group chats or private chats in the \textbf{notification list}.
            \item Includes visual and auditory indicators.
        \end{itemize}
        \item \textbf{View Notifications}
        \begin{itemize}
            \item User checks notifications in the \textbf{notification list}.
            \item Can jump to relevant message/context in the \textbf{notification list}.
        \end{itemize}
    \end{itemize}

    \item \textbf{UI Interactions}
    \begin{itemize}
        \item \textbf{Create Multiple Chats}
        \begin{itemize}
            \item User can have multiple chat sections open.
            \item System limits number of concurrent chats.
            \item User can have only one \textbf{global scope} chat section open.
            \item User can have multiple \textbf{private scope} chat sections open.
        \end{itemize}
        \item \textbf{Upload File}
        \begin{itemize}
            \item User attaches and sends files using \textbf{file upload list}.
            \item System validates file type and size.
        \end{itemize}
        \item \textbf{Select Emoji}
        \begin{itemize}
            \item User adds emojis to messages.
            \item Can browse/search emoji library using \textbf{emoji list}.
        \end{itemize}
    \end{itemize}

    \item \textbf{Administrative}
    \begin{itemize}
        \item \textbf{Moderate Global Chat}
        \begin{itemize}
            \item System enforces character limits for \textbf{chat section}.
            \item Implements spam control measures for the \textbf{global chat}.
        \end{itemize}
    \end{itemize}
\end{itemize}

\subsection{Detailed Use Case Description}
Finally, after all the work we did, we can create a detailed use case description.
Before that, we feel that its very important to mention the difference between chat access point and chat section: a chat access point is a closed down chat section, that hase some functionality of its own, but it is not a chat section. A chat section is a chat access point that is open and has functionality of its own.
\subsubsection{Package: Core Chat Functionality}

\begin{itemize}
    \item 
    Use Case: \textbf{Send Message}

    \textbf{BASIC COURSE:}

    The system displays the chat section. The user types a message in the text input field and clicks the send button. The system sends the message to the server and displays it in the chat section.

    \textbf{ALTERNATIVE COURSES:}

    \textbf{utf8 zero-width characters:}
    User inputs utf8 zero-width space characters in the message. The system removes these characters and sends the message to the server. The system displays the message in the chat section.

    \textbf{empty message:}
    User does not input any message in the text input field. The system does not send the message to the server and displays an error message.

    \textbf{too long message:}
    User inputs a very long message in the text input field (eg. 1000 characters). The system does not send the message to the server and displays an error message.

    \textbf{html editing:}
    User tries to send a message to a group chat or private chat they do not have access to using html editing. The system does not send the message to the server and displays an error message.

    \textbf{cross-site scripting:}
    User inputs a cross-site scripting attack in the message. The system sanitizes the message and sends it to the server. The system displays the message in the chat section.

    \item 
    Use Case: \textbf{Switch between Chats}

    \textbf{BASIC COURSE:}

    The system displays multiple chat access points. User can click on the chat access points to open the chat sections. The system opens the chat section and displays the messages in the chat section. User can click on the close button to close the chat section. The system closes the chat section and displays the chat access point again.

    \textbf{ALTERNATIVE COURSES:}

    \textbf{there are no chat access points:}
    The system displays game room and no chat access points (user has closed down all of them). There are no chat access points to open the chat sections as a result user cannot open the chat sections. The system does not display any error message.

\end{itemize}

\subsubsection{Package: Message Management}
\begin{itemize}
    \item 
    Use Case: \textbf{Edit Message}

    \textbf{BASIC COURSE:}

    The system displays the chat section. User clicks on the edit button to edit the message. The system opens the edit message section and displays the message in the text input field. User edits the message and clicks on the save button. The system sends the edited message to the server and displays it in the chat section.

    \textbf{ALTERNATIVE COURSES:}

    \textbf{message not found (already deleted):}
    User tries to edit a message that does not exist. The system does not send the message to the server and displays an error message.

    \item
    Use Case: \textbf{Delete Message}   

    \textbf{BASIC COURSE:}

    The system displays the chat section. User clicks on the delete button to delete the message. The system opens the delete message section and displays the message in the text input field. User clicks on the delete button. The system sends the delete request to the server and deletes the message from the chat section.
    
    \textbf{ALTERNATIVE COURSES:}

    \textbf{message not found (already deleted):}
    User tries to delete a message that does not exist. The system does not send the message to the server and displays an error message.

    \item
    Use Case: \textbf{Pin Message}

    \textbf{BASIC COURSE:}

    The system displays the chat section (private scope chat). User clicks on the pin button to pin the message. The system sends the pin request to the server and displays the pinned message in the chat section.

    \textbf{ALTERNATIVE COURSES:}

    \textbf{message not found (already deleted):}
    User tries to pin a message that does not exist. The system does not send the message to the server and displays an error message.

    \textbf{message already pinned:}
    User tries to pin a message that is already pinned. The system does not send the message to the server and displays an error message.

    \textbf{global scope chat:}
    User tries to pin a message in the global scope chat. The system does not send the message to the server and displays an error message. User is informed that pinning messages is only available in the private scope chat.

    \item 
    Use Case: \textbf{View Pinned Messages}

    \textbf{BASIC COURSE:}

    The system displays the chat section (private scope chat). User clicks on the pinned messages list to view the pinned messages. The system opens the pinned messages list and displays the pinned messages in the chat section. User inputs text on the search bar on the pinned messages list and clicks on the search button. The system searches for the pinned messages in the chat section and displays the results in the pinned messages list.

    \textbf{ALTERNATIVE COURSES:}

    \textbf{pinned messages not found:}
    User opens the pinned messages list but the private scope chat does not have any pinned messages. The system does not display any pinned messages in the chat section and displays an informational message.

    \textbf{search criteria does not match any pinned messages:}
    User inputs text on the search bar on the pinned messages list and clicks on the search button. The system searches for the pinned messages in the chat section and does not find any pinned messages that match the search criteria. The system does not display any pinned messages in the chat section and displays an informational message.

    \item 
    Use Case: \textbf{Unpin Message}

    \textbf{BASIC COURSE:}

    The system displays pinned messages list. User clicks on the unpin button to unpin the message. The system sends the unpin request to the server and unpins the message from the chat section.

    \textbf{ALTERNATIVE COURSES:}

    \textbf{message not found (already deleted):}
    User tries to unpin a message that does not exist. The system does not send the message to the server and displays an error message.

    \textbf{message already unpinned:}
    User tries to unpin a message that is already unpinned. The system does not send the message to the server and displays an error message.

    \item 
    Use Case: \textbf{Search Messages}

    \textbf{BASIC COURSE:}

    The system displays chat panel. User clicks on the search messages icon which opens seperate section for searching messages. User inputs text on the search bar on the search section and clicks on the search button. The system searches for the messages in the chat section and displays the results in message list. Messages are shown in paginated format. User can scroll down to see more messages. 

    \textbf{ALTERNATIVE COURSES:}

    \textbf{search criteria does not match any messages:}

    User inputs text on the search bar on the search section and clicks on the search button. The system searches for the messages in the chat section and does not find any messages that match the search criteria. The system does not display any messages in the chat section and displays an informational message.

    \textbf{search criteria is empty:}
    User does not input any text on the search bar on the search section and clicks on the search button. The system searches for the messages in the chat section and displays all the messages in the chat section. The system performs view history use case.

    \item 
    Use Case: \textbf{View Message History}

    \textbf{BASIC COURSE:}

    The system displays chat panel. User clicks on the search messages icon which opens seperate section for searching messages. User does not input any text on the search bar on the search section and clicks on the search button. The system searches for the messages in the chat section and displays all the messages in the chat section. Messages are shown in paginated format. User can scroll down to see more messages.

\begin{figure}[H]
    \centering
    \includegraphics[width=0.8\textwidth]{images/SeqDiagrams/CreateGroupChat.png}
    \caption{Create Group Chat Sequence Diagram}
    \label{fig:create-group-section-seq-d}

User opens \textbf{Create Chat}, fills in the chat title and selects members. UI submits this data to \textbf{ChatController}, which synchronously calls \textbf{GroupChatService}. 
The service inserts data synchronously into \textbf{DataBase} to create the group chat and retrieve the generated \texttt{chatId}.

Once the group is created, the \textbf{ChatController} immediately updates the UI to show the new chat access point. 
In parallel, \textbf{NotificationService} sends invites to all selected members asynchronously.


\subsection{Creating Private Chat}

\begin{figure}[H]
    \centering
    \includegraphics[width=0.8\textwidth]{images/SeqDiagrams/CreatePrivateChat.png}
    \caption{Create Private Chat Sequence Diagram}
    \label{fig:create-group-section-seq-d}
\end{figure}

In \textbf{Create Chat} section, user selects \textbf{Private Chat} and chooses a single friend to start a chat with. 
The UI sends this request to the \textbf{ChatController}, which synchronously calls \textbf{ChatService}.  
The service creates a new private chat in the \textbf{Database} and adds both the owner and selected user as members.

Unlike group chat creation, no title or multiple members are involved. 
After creation, the \textbf{ChatController} updates the UI to show chat access, and the \textbf{NotificationService} notifies the invited user asynchronously.


\subsection{Joining existing Group Chat}

\begin{figure}[H]
    \centering
    \includegraphics[width=0.8\textwidth]{images/SeqDiagrams/JoinGroupChat.png}
    \caption{Join existing Group Chat Sequence Diagram}
    \label{fig:join-group-chat-seq-d}
\end{figure}

User clicks on group button and searches for existing group chats. 
The UI sends the name to the \textbf{ChatController}, which synchronously calls \textbf{GroupChatService} to retrieve potential matches from the \textbf{Database}. 
The list of group chats with given name is displayed to the user.

The user then selects a specific chat and clicks the join button. This triggers a request to the \textbf{ChatController}, which looks up the group owner's ID from the \textbf{Database}. 
Once the owner is identified, the controller asynchronously sends a join request to the owner using the \textbf{NotificationService}.

The \textbf{OwnerClient} receives a join request notification and can either approve or reject it. 
If approved, the controller adds the user to the group through \textbf{GroupChatService}, change is saved in \textbf{Database}. 
Simultaneously, the \textbf{NotificationService} notifies the user asynchronously that they were added, and the UI is updated to show access to the group chat.

If the owner rejects the request, the \textbf{NotificationService} notifies user that the request was denied.
